## Будущий цикл работы

В задачах с правилами: один независимый пример поведения → падающая проверка через публичный интерфейс → минимальная реализация → следующий пример. Не создавать заранее весь воображаемый набор тестов. Формулы в expected не копировать из реализации. UI и декоративные изменения проверяются вручную там, где автоматическая проверка ничего не доказывает.

На текущей задаче запускать её конкретный файл/сценарий после изменений. Анализатор GDScript использовать регулярно. Полный набор — перед завершением тикета, где менялись общие правила, и перед вехой. Команды проверки T01 фиксирует с реальной установленной версией движка.

Плановые команды после T01:

```powershell
godot --headless --path game --editor --import
godot --headless --path game --script res://tests/run_tests.gd -- --case port
godot --headless --path game --script res://tests/run_tests.gd
```

Первая команда не объявляется полноценной проверкой типов каждого неиспользованного скрипта: T01 должен обеспечить обнаружение ошибок парсера/типов и ненулевой статус при неудаче во всех игровых и тестовых скриптах. Параметр `--case` реализует наш будущий раннер; это не встроенный параметр Godot. Если движок не находится по имени `godot`, использовать зафиксированный абсолютный путь.

Простой headless-раннер на SceneTree достаточен для старта; сторонний тестовый фреймворк не обязателен. Файловые сценарии используют временный отдельный профиль и не трогают обычное сохранение.

## Критические сценарии

1. Порт первым и болото первым достигают Берегового маяка без выдачи ресурсов отладчиком.
2. Невыгодная покупка оставляет способ восстановить доход.
3. Смена луча не останавливает базовую экономику других районов.
4. Переназначение рабочего не дублирует его и переносимый груз.
5. Пауза/частота кадров/масштабирование карты не создают дополнительную добычу.
6. Сохранение на границе выплаты возвращает ровно один результат.
7. Нулевое масло, отключённое реле, заполненная очередь имеют объяснение и путь восстановления.
8. Отмена сброса ничего не меняет; подтверждённый сброс и загрузка сохраняют точную награду.
9. Ошибка записи или аварийное завершение во время сброса оставляет целый старый либо целый новый профиль. Полный tmp после возвращённой ошибки продвижения игнорируется; будущая версия основного файла блокирует обычную загрузку и autosave даже при наличии старого backup.
10. Второй цикл ускоряется благодаря выбранным технологиям; старые рубежи не дают повторную награду.
11. Профиль M1 загружается в M2 с безопасными значениями новых полей.
12. Все шесть районов участвуют в достижении финала.
13. T12A: одни исходники дают согласованные GLB/2D-выходы корабля/сборщика/порта; base/upgraded различимы в Godot. Неуспешная покупка не меняет модель; успешная временно ускоряет вращение и возвращает прежний темп.
14. Один видимый 3D-инспектор; скрытый не рендерит. Остановка вращения/сниженные эффекты работают, а добыча и XP одинаковы при закрытой/открытой карточке. Изображение экипажа соответствует реальному назначению.
15. Миграция M1 сохраняет действующие лодки, груз и фазы, создаёт необходимый экипаж один раз; пустая лодка M2 не работает, бесплатное восстановление доступно.
16. Три роли доступны без редкого броска; один герой/человек не может работать дважды. Конкретное предложение и контракт выбранной роли показывают цену/качество/шансы; reload не меняет результат/остаток/личность.
17. Личный XP получен действительной работой, не за меню/переназначение/загрузку; личные 12 узлов не принимают эхо и не переносятся после сброса.
18. Общее дерево 36 узлов: оба полных бюджета возвращаются без умножения, включая стоимость проходов; ярус доступен после престижа без отдельного ключа, уровни покупаются заново.
19. Шанс ветерана/модификатора/редкого пассива растёт от выбранных общих талантов, а не cycle_index; контрольный маршрут кампании не требует редкостей.
20. Стартовые материалы/кредиты применяются один раз после подтверждённой раскладки. Preview/cancel/respec/load/ошибка записи не выдают второй старт и не генерируют эхо.

Сценарии 13–20 — будущие критерии владельцев T12A/T17A/T17B/T18/T23, не пройденные проверки этой документационной ветки. Регрессионные тесты оставлять только для реальных границ/ошибок потребителя; статическое сравнение текста спецификации или «проверка, что узлов 36» не доказывает игровые эффекты.

## Ручная проверка и доказательства

Для каждого тикета: начальное состояние/сохранение, действия, наблюдаемый итог. Для M1 и M2: журнал прохождения, сборка и список известных ограничений. T13/T22 фиксируют фактическую длительность, а не только изменение коэффициентов.

Доступность: клавиатура, увеличенный текст, состояния не только цветом, остановка вращения/эффектов без потери характеристик. Производительность: профиль, устройство, разрешение, число объектов и измеренные значения; отдельно карта без карточки, один инспектор, смена объектов и закрытие. T12A фиксирует первоначальный бюджет, T23 проверяет полный арт/людей/поздний профиль. Верхнеуровневые лимиты из чужого навыка не считать замерами проекта.

REVIEW.md — историческая запись независимой проверки исходного плана, не доказательство будущей игры или новых моделей.
